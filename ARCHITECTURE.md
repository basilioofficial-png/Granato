# granato — Архитектура MVP

## 1. Технологический стек

| Технология | Назначение |
|---|---|
| React Native + Expo (SDK 57) | Мобильное приложение |
| TypeScript (strict) | Строгая типизация |
| Expo Router | Навигация на основе файлов в папке `app/` |
| Expo SQLite | Локальная база данных, источник истины на устройстве |
| Zustand | Состояние интерфейса |
| Supabase (PostgreSQL, Auth, RLS) | Аккаунты, серверное хранение, защита данных |
| Jest + `jest-expo` | Автоматические тесты |
| ESLint (`expo lint`) | Проверка качества кода |

Зависимости устанавливаются только через `npx expo install <пакет>`: эта команда подбирает версии, совместимые с текущим Expo SDK.

Примечание: пакеты `react-native-reanimated`, `react-native-worklets` и `react-dom` явно закреплены в `package.json`, хотя напрямую не используются. Их требуют внутренние зависимости Expo Router; без явного закрепления npm ставит более новые версии, несовместимые с Expo Go для SDK 57.

## 2. Ключевые принципы

1. **Local-first.** Любое действие сначала записывается в SQLite в транзакции. Интерфейс обновляется после успешной записи. Сеть никогда не нужна для основных функций.
2. **Время — это метки, а не тики.** Хранится момент начала и момент окончания в UTC. Таймер интерфейса только отображает `now − started_at` и ничего не сохраняет.
3. **Логика отделена от интерфейса.** Вся логика времени и аналитики — чистые функции TypeScript в `src/domain/`, без React, без базы, без `Date.now()` внутри (текущее время передаётся аргументом). Их легко тестировать.
4. **Интервалы не пересекаются.** Инвариант обеспечивается domain-слоем при каждом изменении.
5. **Мягкое удаление.** Записи и категории не удаляются физически: ставится `deleted_at` (для синхронизации и отмены).
6. **Минимум зависимостей.** Новая библиотека добавляется только с обоснованием.

Тесты лежат рядом с кодом: `foo.ts` → `foo.test.ts`. Импорт из `src` — через алиас `@/` (например, `@/domain/time`).

Экраны находятся в `src/app/` — это текущее соглашение Expo Router для SDK 57; весь остальной код тоже внутри `src/`, вне папки `app/`.

**Направление зависимостей:** `app → store → services → domain` и `services → db`. Модуль `domain` не импортирует ничего из других слоёв. Экраны не обращаются к базе напрямую.

## 4. Модель данных

### 4.1. Категории и активности — одна сущность

Активность — это узел дерева категорий. Связь через `parent_id` (список смежности). Запись времени ссылается на любой узел дерева. Это позволяет пользователю самому выбирать глубину детализации для каждой сферы жизни без изменения модели данных.

```
Работа                   ← можно записывать время сюда
├── Совещания            ← или сюда
│   └── Встречи с командой  ← или сюда
└── Программирование
Отдых                    ← без детализации
```

### 4.2. Схема SQLite (локальная)

Время хранится как `INTEGER` — миллисекунды Unix epoch (UTC).

```sql
CREATE TABLE categories (
  id            TEXT PRIMARY KEY,          -- UUID v4, генерируется на устройстве
  user_id       TEXT,                      -- NULL до входа в аккаунт
  parent_id     TEXT REFERENCES categories(id),
  name          TEXT NOT NULL,
  color         TEXT NOT NULL,             -- '#RRGGBB'
  icon          TEXT,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  favorite_rank INTEGER,                   -- NULL = не в избранном; иначе порядок кнопки
  archived_at   INTEGER,                   -- скрыта из выбора, история сохраняется
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER,
  sync_status   TEXT NOT NULL DEFAULT 'pending'  -- 'pending' | 'synced'
);

CREATE TABLE time_entries (
  id           TEXT PRIMARY KEY,
  user_id      TEXT,
  category_id  TEXT NOT NULL REFERENCES categories(id),
  started_at   INTEGER NOT NULL,
  ended_at     INTEGER,                    -- NULL = запись активна (идёт сейчас)
  timezone     TEXT NOT NULL,              -- IANA, например 'Europe/Moscow', на момент начала
  source       TEXT NOT NULL,              -- 'live' | 'manual'
  is_edited    INTEGER NOT NULL DEFAULT 0, -- 1 = границы правились вручную
  note         TEXT,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER,
  sync_status  TEXT NOT NULL DEFAULT 'pending',
  CHECK (ended_at IS NULL OR ended_at >= started_at)
);

-- Гарантия «только одна активная запись» на уровне базы
CREATE UNIQUE INDEX one_running_entry
  ON time_entries ((1)) WHERE ended_at IS NULL AND deleted_at IS NULL;

CREATE INDEX time_entries_started ON time_entries (started_at);

CREATE TABLE experiments (
  id            TEXT PRIMARY KEY,
  user_id       TEXT,
  duration_days INTEGER NOT NULL CHECK (duration_days IN (7, 14, 30)),
  started_at    INTEGER NOT NULL,
  ends_at       INTEGER NOT NULL,
  timezone      TEXT NOT NULL,
  status        TEXT NOT NULL,             -- 'active' | 'completed' | 'cancelled'
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER,
  sync_status   TEXT NOT NULL DEFAULT 'pending'
);

CREATE TABLE app_meta (                    -- служебные флаги (default_categories_seeded, last_pulled_at)
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

Версия схемы ведётся через `PRAGMA user_version`. Миграции применяются последовательно при старте приложения; каждая миграция вместе с повышением версии выполняется в одной транзакции, поэтому «наполовину применённой» миграции не бывает. База от более новой версии приложения не открывается (защита от отката приложения).

### 4.2.1. Доступ к базе

- Код работает с базой через собственный интерфейс `SqlDatabase` (`src/db/types.ts`): `exec`, `run`, `get`, `all`, `transaction`.
- На телефоне его реализует `expo-sqlite`, в тестах — встроенный SQLite Node.js (`node:sqlite`, Node ≥ 22.13). Поэтому миграции и запросы проверяются автотестами на настоящем движке SQLite.
- Используется **синхронный** API `expo-sqlite`: синхронную транзакцию невозможно «перемешать» с посторонними запросами, а объёмы данных малы. Если аналитика по большим периодам начнёт заметно тормозить интерфейс, тяжёлые запросы будут переведены на асинхронный API.
- Репозитории не открывают транзакции сами — транзакциями управляют сервисы.
- Стартовые категории создаются один раз; флаг `default_categories_seeded` в `app_meta` не даёт пересоздать их, если пользователь удалил все категории.

### 4.3. Схема Supabase (серверная, этап 12)

Повторяет локальную с типами PostgreSQL:
- `uuid` для идентификаторов;
- `timestamptz` для времени;
- `user_id uuid NOT NULL REFERENCES auth.users(id)`;
- `sync_status` на сервере отсутствует (локальное поле);
- `server_updated_at timestamptz` — проставляется триггером, используется для инкрементальной загрузки.

Дополнительно таблица `profiles (id = auth.users.id, timezone, created_at, updated_at)`.

### 4.4. Пользователи

- До входа в аккаунт приложение работает локально, `user_id = NULL`.
- При первом входе всем локальным строкам проставляется `user_id` текущего пользователя, и они ставятся в очередь синхронизации.
- Аутентификация — Supabase Auth, вход по одноразовому коду на email (без паролей).

## 5. Работа со временем

### 5.1. Хранение
- Все моменты — UTC (мс epoch в SQLite, `timestamptz` в Postgres).
- В каждой записи сохраняется IANA-часовой пояс на момент начала. Он используется, чтобы определить, к какому «дню пользователя» относится время, даже после смены часового пояса или перехода на летнее время.

### 5.2. Источник текущего времени
- В domain-функции текущее время всегда передаётся параметром `now`. Это делает функции детерминированными и тестируемыми.
- В сервисах используется модуль `src/lib/clock.ts` (обёртка над `Date.now()`), который подменяется в тестах.

### 5.3. Операции трекинга (транзакционно)

| Операция | Действие |
|---|---|
| `start(categoryId)` | Если есть активная запись — выполнить `switch`. Иначе создать запись `started_at = now, ended_at = NULL, source = 'live'` |
| `stop()` | Активной записи проставить `ended_at = now` |
| `switch(categoryId)` | Одной транзакцией: активной записи `ended_at = T`, новая запись `started_at = T` (одна и та же метка `T`) |
| Восстановление | При старте приложения прочитать запись с `ended_at IS NULL` и показать `now − started_at` |

Повторное нажатие на уже активную категорию ничего не делает (защита от двойного тапа).

### 5.4. Инварианты
1. Не более одной активной записи (дополнительно гарантирует уникальный индекс).
2. `ended_at ≥ started_at`.
3. Неудалённые записи не пересекаются. Проверка выполняется в `domain/time` перед каждым сохранением правки. При конфликте сервис возвращает описание конфликта, интерфейс предлагает подрезать соседнюю запись.
4. Записи не разрезаются по полуночи при хранении. Деление по дням выполняется только при расчёте аналитики (обрезка интервала границами периода).

### 5.5. Аномалии часов
Если `now < started_at` активной записи (часы переведены назад), длительность не показывается отрицательной: интерфейс сообщает о проблеме и предлагает исправить запись вручную.

## 6. Аналитика

Реализуется чистыми функциями в `src/domain/analytics/`.

- **Обрезка по периоду.** Каждый интервал пересекается с периодом `[from, to)`. Учитывается только попавшая внутрь часть. Активная запись считается до `now`.
- **Агрегация по иерархии.** Собственное время узла (записи прямо на него) + время всех потомков = полное время узла. Каждая запись принадлежит ровно одному узлу, поэтому двойного подсчёта нет.
- **Проверка корректности.** Сумма полного времени корневых категорий = общему учтённому времени (проверяется тестами).
- **Учтённое время** — сумма длительностей записей в периоде.
- **Полнота** = учтённое время / длительность периода (для текущего периода — до `now`).
- **Точность** = время записей с `source = 'live'` и `is_edited = 0` / учтённое время.
- **Сравнение периодов** — разница полного времени по каждой категории между двумя периодами.
- Результат аналитики — сериализуемая структура (JSON). Это и есть будущий вход для ИИ-аналитика.

## 7. Состояние приложения (Zustand)

- Store хранит только то, что нужно экранам: активная запись, список категорий, выбранный день истории.
- Store не является источником истины. Источник истины — SQLite. Store обновляется после успешной записи в базу.
- Секундный тик таймера живёт в отдельном хуке экрана, а не в глобальном store, чтобы не перерисовывать всё приложение.
- Хук таймера `useNow` привязан к id активной записи: при старте или переключении «текущее время» обновляется в том же рендере, иначе новая запись на мгновение выглядела бы начатой «в будущем». При возврате приложения из фона время пересчитывается сразу.
- Действия трекинга (`start`, `stop`) выполняет `trackingService`: он берёт одну метку времени на всё действие, получает план от `domain/tracking` и записывает его одной транзакцией.

## 8. Синхронизация (проект; реализация — этап 13)

На первом этапе синхронизация не реализуется. Ниже — согласованный проект.

### 8.1. Модель
- Каждая строка имеет `id` (UUID с устройства), `updated_at`, `deleted_at`, локальный `sync_status`.
- Любое локальное изменение ставит `sync_status = 'pending'` и обновляет `updated_at`.

### 8.2. Алгоритм v1
1. **Push.** Отправить все строки `pending` через `upsert` в Supabase. После успеха — `sync_status = 'synced'`.
2. **Pull.** Загрузить строки, у которых `server_updated_at > last_pulled_at` (хранится в `app_meta`). Применить локально.
3. **Конфликт** — last-write-wins по `updated_at`. Локальная строка `pending` не перезаписывается более старой серверной версией.
4. Запуск синхронизации: при старте приложения, при возврате в приложение и после изменений (с задержкой). Без фоновых задач.

### 8.3. Ограничения v1
- Рассчитано на одно устройство. При работе с двух устройств возможны пересекающиеся интервалы — их разрешение запланировано после MVP.
- Удаления передаются как `deleted_at` (мягкое удаление).

## 9. Безопасность

- В приложении хранятся только публичные значения: `EXPO_PUBLIC_SUPABASE_URL` и `EXPO_PUBLIC_SUPABASE_ANON_KEY`. Ключ `service_role` никогда не попадает в код приложения и в репозиторий.
- Файл `.env` с реальными значениями — в `.gitignore`. В репозитории — `.env.example`.
- На всех серверных таблицах включён RLS:

```sql
ALTER TABLE time_entries ENABLE ROW LEVEL SECURITY;

CREATE POLICY "own rows: select" ON time_entries
  FOR SELECT USING (user_id = auth.uid());
CREATE POLICY "own rows: insert" ON time_entries
  FOR INSERT WITH CHECK (user_id = auth.uid());
CREATE POLICY "own rows: update" ON time_entries
  FOR UPDATE USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid());
CREATE POLICY "own rows: delete" ON time_entries
  FOR DELETE USING (user_id = auth.uid());
-- аналогично для categories, experiments, profiles
```

- Сессия Supabase хранится в защищённом хранилище устройства (`expo-secure-store`), подключается на этапе 12.
- Любое изменение серверной схемы — только SQL-миграцией в `supabase/migrations/`.

## 10. Задел под ИИ-аналитика (версия 2.0)

- Аналитика возвращает структурированные агрегаты (раздел 6) — готовый вход для ИИ.
- ИИ вызывается только с сервера (Supabase Edge Function). Ключ ИИ-провайдера хранится в секретах Supabase, не в приложении.
- В приложении появится только экран с результатами и запрос к Edge Function.
- Сейчас под ИИ ничего не реализуется.

## 12. Технические риски

| Риск | Мера |
|---|---|
| Сложность редактирования истории | Отдельный этап, логика в тестируемых чистых функциях, явная обработка конфликтов |
