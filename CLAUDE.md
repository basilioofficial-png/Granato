# CLAUDE.md — инструкции для Claude Code в проекте granato

## Контекст

granato — мобильное приложение для осознанного учёта времени (React Native + Expo + TypeScript). Основатель продукта не профессиональный разработчик: Claude отвечает за техническую реализацию, архитектуру и качество кода.

Перед работой прочитай:
- `PRD.md` — что строим и зачем;
- `ARCHITECTURE.md` — как устроено приложение (обязательно перед изменением кода);
- `ROADMAP.md` — текущий этап и критерии приёмки.

## Общение

- Язык общения и документации — русский. Код, имена файлов, переменных, таблиц и коммитов — на английском.
- Объясняй решения простыми словами, пошагово: смысл, преимущества, недостатки, риски, рекомендуемый вариант.
- Не заставляй выбирать между эквивалентными техническими деталями — принимай обоснованное решение сам.
- Перед реализацией существенной функции покажи краткий план.
- Сообщай о технических ограничениях до реализации.
- Не утверждай, что функция работает, если она не проверена. Явно разделяй «проверено тестами» и «требует ручной проверки на телефоне».
- Основное устройство для ручной проверки — iPhone (Expo Go).

## Порядок выполнения задачи

1. Определи этап в `ROADMAP.md`, к которому относится задача.

4. Запусти проверки (см. ниже) и исправь ошибки.
5. Обнови статус этапа в `ROADMAP.md` и документацию, если изменилась архитектура.
6. Закоммить с понятным сообщением на английском.
7. Дай отчёт в формате:
   - **Что сделано**
   - **Изменённые файлы**
   - **Проверки и их результаты**
   - **Что проверить вручную** (пошагово, для iPhone)

## Команды проверки

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # expo lint
npm test            # jest
npm run doctor      # expo-doctor: проверка совместимости зависимостей и конфигурации
npx expo start      # запуск dev-сервера (ручная проверка в Expo Go)
```

Дополнительная проверка сборки без телефона: `npx expo export --platform ios --output-dir <временная папка>` — собирает JS-бандл и ловит ошибки импорта и маршрутов.

В облачной среде Claude Code серверы Expo (`api.expo.dev`, `exp.host`) недоступны: используй `EXPO_OFFLINE=1 npx expo install ...` — версии берутся из встроенной таблицы `expo/bundledNativeModules.json`. Проверки `expo-doctor`, требующие сети, в облаке не проходят — это не ошибка проекта.

Перед каждым коммитом с кодом `typecheck`, `lint` и `test` должны проходить.

## Архитектурные правила

- Слои: `src/app/` (экраны, Expo Router) → `src/store/` → `src/services/` → `src/domain/`; `src/services/` → `src/db/`.
- `src/domain/` — только чистые функции TypeScript: без React, без SQLite, без сети, без `Date.now()`. Текущее время передаётся параметром `now`.
- Экраны не обращаются к базе напрямую и не содержат бизнес-логику.
- Источник истины на устройстве — SQLite. Zustand-store отражает базу и обновляется после успешной записи.
- Любое действие пользователя сначала надёжно записывается в SQLite (в транзакции), сеть для основных функций не требуется.

## Правила работы со временем

- Время хранится в UTC: `INTEGER` миллисекунды epoch в SQLite, `timestamptz` в Postgres.
- Продолжительность всегда вычисляется по меткам: `(ended_at ?? now) − started_at`. Таймер интерфейса ничего не сохраняет.
- Не более одной активной записи (`ended_at IS NULL`).
- Переключение — одна транзакция, одна метка времени `T` для конца старой и начала новой записи.
- Интервалы не пересекаются; проверка — в `src/domain/time`.
- Записи не разрезаются по полуночи при хранении; деление по дням — только в аналитике.
- Для дат используй встроенные `Date` и `Intl`. Библиотеку дат добавляй только с обоснованием.

## Код

- TypeScript `strict` (+ `noUncheckedIndexedAccess`). Запрещены `any`, `@ts-ignore`, `as unknown as`. Нестрогие места — через явные типы и проверки.
- Идентификаторы сущностей — UUID v4, генерируются на устройстве.
- Удаление пользовательских данных — мягкое (`deleted_at`).
- Комментарии — по делу, объясняют «почему», а не «что».
- Не используй моковые или демо-данные незаметно вместо реальных. Тестовые данные — только в тестах.
- Логика времени и аналитики обязательно покрывается тестами в том же изменении.
- Тесты лежат рядом с кодом (`foo.test.ts`), импорты из `src` — через алиас `@/`.

## Зависимости

- Устанавливай только через `npx expo install <пакет>` — для совместимости с текущим Expo SDK. Dev-инструменты: `npx expo install <пакет> -- --save-dev`; после установки проверь, что пакет попал в нужный раздел `package.json`.
- После установки проверь `npm ls` на отсутствие `invalid` и `missing`.
- Каждую новую зависимость обоснуй: зачем нужна, почему нельзя без неё.
- Минимизируй количество зависимостей.

## База данных

- Любое изменение структуры локальной базы — новая миграция в `src/db/migrations/` (существующие миграции не редактируются после коммита).
- Любое изменение серверной схемы — SQL-миграция в `supabase/migrations/`.
- Каждая серверная таблица с пользовательскими данными имеет `user_id` и RLS-политики `user_id = auth.uid()` на select/insert/update/delete.

## Безопасность

- В приложении допустимы только публичные ключи (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`).
- Ключ `service_role` и любые серверные секреты никогда не попадают в код приложения и в репозиторий.
- `.env` — в `.gitignore`; в репозитории только `.env.example`.
- Ключи ИИ-провайдеров (версия 2.0) — только в секретах Supabase Edge Functions.

## Запрещено без подтверждения основателя

- Разрушительные операции: удаление данных, `git push --force`, `git reset --hard`, удаление веток, сброс или удаление базы, удаление таблиц и колонок.
- Изменение согласованной архитектуры или состава MVP.
- Переход к следующему этапу ROADMAP до приёмки текущего.
- Реализация функций вне MVP (ИИ, виджеты, уведомления и т. п.).

## Не усложняй

- Не добавляй архитектуру «на будущее», если она не нужна текущему этапу.
- Синхронизация реализуется только на этапе 13 и по проекту из `ARCHITECTURE.md`.
